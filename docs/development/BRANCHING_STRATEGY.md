# استراتيجية الفروع — BRANCHING_STRATEGY

> آخر تحديث: الدورة 3 (إعادة هيكلة المستودع). هذا الملف حاكم وملزم لكل عمل جديد.

## الأدوار

| الفرع | الدور | المصير |
|---|---|---|
| `main` | **الإنتاج** — آخر إصدار مستقر ومعتمد فقط | يُنشر منه حصرياً؛ كل commit فيه يجب أن يكون قابلاً للنشر |
| `develop` | **التكامل** — أحدث التغييرات المدمجة والمختبرة تكاملياً | يُدمج دورياً في main عبر Release PR |
| `feature/*` | إضافة ميزة | من develop ← يعود إلى develop |
| `fix/*` | إصلاح خلل | من develop ← يعود إلى develop |
| `refactor/*` | تحسين بنيوي بلا تغيير سلوك | من develop ← يعود إلى develop |
| `perf/*` | تحسين أداء | من develop ← يعود إلى develop |
| `test/*` | إضافة/تحسين اختبارات | من develop ← يعود إلى develop |
| `chore/*` | صيانة، وثائق، أدوات | من develop ← يعود إلى develop |
| `release/*` | تحضير إصدار | من develop ← يُدمج في main (Release PR) |
| `hotfix/*` | إصلاح إنتاجي حرج | **من main** ← يُدمج في main **وفي develop** |
| `archive/*` | نسخ محفوظة قبل ترحيلات كبرى | لا تُحذف أبداً |

## القواعد الحاكمة

1. **كل فرع عمل جديد يبدأ من `origin/develop` بعد تحديثه** (`git fetch origin` ثم التفرع منه).
2. العودة إلى develop **دائماً عبر Pull Request** مع CI أخضر — لا دفع مباشر.
3. يُدمج develop في main **عبر Release PR** فقط، مع ترقيم SemVer وTag.
4. **النشر الإنتاجي من main فقط**، ومن Tags تشير إلى commits في تاريخ main.
5. `hotfix/*` من main للإصلاحات الحرجة، ويجب إعادة دمجه في develop لمنع اختلاف دائم.
6. **ممنوع**: force push على main/develop، حذف التاريخ، إعادة إنشاء المستودع، تجاوز فحوص CI.
7. فروع الأرشيف (`archive/*`) وفروع التاريخ (`huda-web-app`, `dev/audit-p0`, `dev/offline-pwa`, `save`) محفوظة ولا تُحذف تلقائياً.
8. فروع العمل المؤقتة تُحذف من remote فقط بعد دمج PR بنجاح (اختياري، آمن).

## التسمية

- صيغة: `<type>/<وصف-قصير-kebab-case>` مثل: `feature/audio-downloads`، `fix/reader-bugs`.
- الاسم يصف الغرض؛ يُفضّل ربطه برقم Issue: `fix/11-rate-limit-sqlite`.

## الحماية

- تُفعَّل قواعد حماية main وdevelop عبر GitHub (Branch Protection/Rulesets) بقدر صلاحيات المالك:
  - اشتراط نجاح CI، منع force push، منع الحذف، منع الدمج مع تعارضات.
  - **لا يُشترط عدد موافقات** (مستودع مطور واحد) — الاشتراط الوحيد هو نجاح الفحوص.
- تفاصيل التنفيذ الحالية: `docs/audit/IMPLEMENTATION_LOG.md` (الدورة 3).

## لماذا هذا النموذج؟

- main يمثل دائماً ما يعمل في الإنتاج فعلاً (لا مفاجآت).
- develop نقطة تكامل وحيدة تُختبر عليها المجموعات قبل الإصدار.
- العزل عبر فروع العمل يمنع تسريب أعمال نصف منتهية إلى التكامل.
- التاريخ غير المدموج بين main القديم والتطبيق الحديث حُفظ عبر أرشيفات `archive/*` (الدورة 3).
